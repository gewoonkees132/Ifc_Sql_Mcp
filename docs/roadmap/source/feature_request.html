What it cannot do yet

  • You cannot see what it counted. Answers are numbers and names, never a view of the model.F01–F03
  • Only software checks the answers. No architect's verdict is recorded, so the tool cannot learn what is right on a real project.F04–F09
  • Areas come as IFC quantities, not as the categories of SIA 416, DIN 277 or NEN 2580, not by cost group and not as carbon.F10–F13
  • Results stay in the chat. No Excel for the cost consultant, no BCF for Revit.F14
  • It runs on one machine, for one person, and keeps no record of what it answered.F15–F20
02 · Why participatory

The tool measures. You decide.

The November audit checked every answer against an independent reading of the file, and the 22 things it found are fixed. It also showed where a referee in software stops being enough.

8,090.7 → 4,721.4 m²

The office's room total. Every room's area was correct; the total was not, because Revit wrote its Rooms and its MEP Spaces for the same floor. The tool now finds the 75 copies from the plans.

Whether 69 Meeting Room is a room of its own or a copy inside 54 EDP I is something the project architect knows in a second, and software can only infer.

1,458 errors → 0

Is the tower fit for handover? The rule engine counted 1,458 errors, none of them the architect's to fix. The useful answer came from Claude reading the model: “Default Wall” on 6,024 walls, no rooms, placeholder project information.

The rules are fixed. The lesson stays: the judgement that matters is a person's, and nothing keeps it today.

So every feature in this document keeps a person where judgement is needed, and stores what they decided as data: who, when and why. A verdict that is stored can be counted, replayed and turned into a test. That is a participatory audit.

A participatory audit session, in 45 minutes

1

Bring

One current export of a live project. The database runs on your own machine; Claude sees only the results of its queries.

2

Ask

The questions you would ask anyway: wall area for the cost plan, a door schedule, room areas, fit for handover, what changed.

3

Mark

Each answer right, wrong or can't tell. Write the right figure if you know it, and why.

4

Keep

Every “wrong” becomes a test that fails until it is fixed, the way the audit's 22 findings were.

Red marks where a person decides: the vote boxes, the note boxes, and on each feature the line “You decide”. Everything in black is what the tool proposes.

06 · For a technical reader

The data work behind it

The tool is a data pipeline with an assistant on top. This roadmap grows it the way data work grows in a practice: from one person's laptop to shared, governed data, with the people who know the buildings checking the answers.

Built today

  • Ingest. IfcOpenShell extract, a pure transform, and one transaction per model, with COPY for the bulk tables. Each file is identified by its SHA-256; every attempt is recorded.
  • Store. PostgreSQL 16, 14 tables and 8 views, every one commented. Units normalised to m, m², m³. Quantities keep their source and a precedence.
  • Quality. 45 rules in one YAML catalogue. Each finding is scoped to the model or the loader; runs are recorded so quality can be compared over time.
  • MCP. 11 tools on a read-only role, every result bounded. run_sql passes a validator, a single-SELECT cursor, a read-only transaction with timeouts, and the role's privileges.
  • Evidence. 1,087 tests at 100 % branch coverage and 130 on real exports; CI on Linux and Windows; 13 decision records; two audits with figures before and after.

Five rules every feature keeps

1The assistant reads. Anything that changes rules, mappings or verdicts is approved by a person.
2Every figure names its source and its coverage.
3Unknown is not zero. A total over missing values is null, with a warning.
4What a person decides is stored as data: who, when and why.
5A feature is done when its figure, measured before and after, matches what an architect says is right.
